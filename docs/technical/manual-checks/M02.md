# M02 — The compile inside Obsidian: the spike (US-008 AC-1, AC-12)

Part of the [manual checks](../manual-checks.md).

**When:** after ticket #13 (the spike build), before ticket #14 builds on it; and
after any change to the worker, the embedded assets or the build.

**Needs:** Obsidian desktop on the author's machine. Prepared by the developer
(SCAR-012, SCAR-018): a scratch vault made with the generator (the real vault is
never used), its checksum list taken **before** the install
(`spikes/m01-before.txt`, 12 files; unchanged after it), the build installed
with its own version, and the checksums of the installed files equal to the fresh
build's (in the hand-over note). Restart Obsidian once so the build is loaded;
turn off Restricted mode and enable the plugin in Settings, Community plugins.

**Expected version:** the version in the hand-over note (the plugin's entry in
Community plugins). If it differs, stop: the wrong build is installed.

**What the build has:** one developer command, `Spike: compile a fixed sheet`,
which compiles a fixed sheet of nine invented cards in the embedded worker and
shows a notice and a console line: milliseconds, pages, bytes, fit facts, the
JavaScript heap and the SHA-256 of the PDF.

**Reference (measured in Node, 2026-11-12, the same source, typst.ts 0.7.0):**
1 page, 29 068 bytes, 9 fit facts, SHA-256
`6b9b67c1ea0d33756ee8f7eb2e988be7ed4c1e5ec35edbbe9ffb39bfb33a01a6`
(two compiles in Node give the same hash). **Not measured:** that Obsidian's
Electron worker gives the same bytes; this check measures it (SCAR-045). A
different hash is a finding to report, not a failure to hide.

## Steps

1. Open the scratch vault (Open folder as vault). Settings, Community plugins:
   the plugin is on, its version is the expected one. Open the developer console
   (Cmd+Option+I): **no red error** from the plugin. Open its Network tab and clear it.
2. Command palette, `Spike: compile a fixed sheet (developer)`. **Report** the
   first notice (time, pages, bytes, facts, heap) and the console line's SHA-256.
   Expected from the reference: 1 page, 29068 bytes, 9 fit facts.
3. Run the command twice more. **Report** both times. **Expected:** the second
   is faster than the first.
4. Network tab: **no request** was made by any of the three runs (nothing is
   downloaded). Report any entry that appeared.
5. Memory: **report** the heap from the notice after the first and the third run,
   and, if you like, the memory of the Obsidian helper process in Activity
   Monitor before the first run and after the third.
6. Settings, Community plugins: turn the plugin off and on. **Expected:** no
   console error; run the command once more: it compiles. (A first run after
   enabling is a first run again: slower is normal.)
7. Report the machine, the macOS and Obsidian versions.

## Findings after the run (2026-11-12)

**The 152 ms `[Violation] 'setTimeout' handler` line on the first compile.**
Looked at in Node, not in Obsidian (the numbers are indications; Electron's V8
and Obsidian's loader differ), on this machine, with the real embedded compiler
(28 325 178 bytes, 14 310 928 base64 characters, gzip):

| Step (main thread unless said) | Time |
|---|---|
| `atob` of the text | 2.6 to 3.6 ms |
| the `charCodeAt` loop over the result | 14.5 to 15.3 ms |
| gunzip with `DecompressionStream` (a stream; yields) | 82 to 110 ms elapsed |
| `copy()` of the 28 MB buffer for the hand-over | 1.3 to 3.7 ms |
| cold parse of the 15.6 MB `main.js` (when the plugin is enabled) | 56 ms (+ 9 ms to read), then 3 to 5 ms |

So the synchronous decode on the first compile is about 25 ms, not 152 ms; the
one big synchronous piece known is the parse of `main.js`, and that happens when
the plugin loads, not at the first compile. **Not established:** which event the
violation belongs to (plugin load, a chunk of the gunzip stream, or something of
Obsidian's own: the log line has no stack of ours). No change was made. The
cheapest decisive step is a spike build that logs Chromium's long-task entries
(`PerformanceObserver` with `longtask`) with time stamps at plugin load and
around the compile, run once by the author; the fix, if it is ours, would move
the decode into the worker (the init message would carry the text, not the
buffers), which changes AC-7 and its tests, so it needs a story amendment first.

**The deprecation warning** (`using deprecated parameters for the initialization
function`) comes from typst.ts 0.7.0's own start-up call inside the worker; it is
not ours and not an error. A fix would be to pass the module as one options
object (`{module_or_path}`), which is typst.ts's code, not the plugin's: no
action, recorded.

## Follow-up run: where does the 152 ms come from? (build 0.1.0-m01.2)

Test build only: it logs lines starting `GCC trace` to the console, on the page's
clock (`performance.now`, the same clock as Chromium's long-task entries), and
changes no behaviour. The trace is removed before a release.

**Installed 2026-11-12:** version `0.1.0-m01.2` in the scratch vault; `main.js`
SHA-256 `b6099327514ddfa646af02f38ac66adb47cf963e2dc8e52dfdc68791e8986a9c`,
`styles.css` `c7ce7616…632b` (unchanged), `manifest.json`
`ff5f7112…e98d` (the version differs). The 12 notes of the vault are unchanged;
five files in `.obsidian/` (`app.json`, `appearance.json`,
`community-plugins.json`, `core-plugins.json`, `workspace.json`) were written by
Obsidian itself when the vault was first opened.

**What the trace shows:** `GCC trace onload <ms>` when the plugin loads;
`longtask` and `long-animation-frame` entries (the second names the scripts that
ran, with their `invoker`, for example a `setTimeout` handler, and their
`sourceURL`), including those from before the plugin loaded (replayed);
`compilerWasm`, `fonts` and `startWorker` with `start` and `end`; and `compile
start` and `compile end` around the whole command. If an entry is not supported
by this Obsidian, a line says so.

**Steps**

1. Quit Obsidian (Cmd+Q) and open the scratch vault again. Open the developer
   console (Cmd+Option+I), Console tab, and tick **Preserve log** in its
   settings (the gear).
2. Command palette, `Reload app without saving` (this loads the plugin with the
   console open). Wait until Obsidian is idle.
3. Settings, Community plugins: the version is `0.1.0-m01.2`.
4. Run `Spike: compile a fixed sheet (developer)` **once**.
5. In the console filter box type `/GCC trace|Violation/` and copy every line
   (select all, copy), including any `[Violation]` line.
6. Optional: run the command a second time and copy the new lines.

**Reading the result (decided before the run, SCAR-032):** the violation belongs
to the event whose time range contains its own entry. A `long-animation-frame`
entry with `invoker` naming our timer or a `sourceURL` of our plugin is ours; one
that names Obsidian's own files is not. If the long entry sits between
`compilerWasm start` and `end`, the decode is the cause; if it is at `onload`,
the parse of `main.js` is; if it is at `startWorker`, the worker start is.

| Item | Result (author's run, build `0.1.0-m01.2`, M1 MacBook, macOS 27.0.1, Obsidian 1.15.0; times in ms on the page's clock) |
|---|---|
| version shown | not stated in the paste (the trace lines come from `0.1.0-m01.2`) |
| long entries at load | The plugin's `onload` is logged at 1143.6 (first load) and 571.2 (after the reload). Each lies at the **end** of a long task: 890.6 + 253 = 1143.6, and 359.7 + 217 = 576.7. | long entries during the compile | `compile start` 12225.4; `compilerWasm start` 12240.8 (15 ms of our sheet preparation before it); a **long task 12223.3 + 113 = 12336.3** (starts at the click, `firstUIEventTimestamp` 12219.1; no script attribution); a **long-animation-frame script 12340.2 + 60.6**, `invoker: Promise.resolve` (a promise continuation, no source name); `compilerWasm end` 12404.9; `fonts` 12405.0 to 12419.5; `startWorker` 12419.6 to 12420.4; `compile end` 12660.3 (435 ms, as the notice) |
| the `[Violation]` line | **Not reproduced during the compile**: no violation line appeared there in this run. The only one, `'setTimeout' handler took 96ms` from `app.js:41` (Obsidian's file), is at 11592.5, before the reload, in the first session, which ran no compile of ours |
| trace lines | in the author's paste; summarised above |

**Reading (by the rule written before the run).** The long entries of the compile
lie between `compilerWasm start` (12240.8) and `compilerWasm end` (12404.9): the
decode took 164 ms wall, and of it **95.5 ms** (12240.8 to the end of the long
task, 12336.3) plus **60.6 ms** (the promise continuation) block the main thread:
**about 156 ms in two tasks, close to the 152 ms first seen**. The same decode
measured 25 ms of synchronous work in Node, so Electron is several times slower
here (not measured why). Fonts (14.5 ms) and the worker start (0.8 ms) are small.
The rest of the compile (435 − 195 = about 240 ms) is the worker, off the main
thread. The second and later compiles decode nothing (6 to 9 ms, M02 step 3).

**Not established:** that all of those 156 ms are the decode's own steps (the
long task also holds the click handling and a little of our sheet preparation;
the paste has no script names); the plugin load's own share of the 217 to 253 ms
tasks (needs a time stamp at the very top of the bundle, or a run with the plugin
off for comparison); why the `[Violation]` line of the first run did not repeat.
